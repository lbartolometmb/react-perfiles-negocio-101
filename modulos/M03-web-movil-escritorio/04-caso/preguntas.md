## Para devolver una propuesta que dice «React en todos los canales»

1. ¿Cuál es la URL pública del aviso, y está el texto en el fuente?
2. ¿El panel se usa con el navegador que ya hay en sala? Si sí, ¿qué gana empaquetarlo?
3. ¿La ronda tiene foto y cola offline? ¿Quién acepta el techo si se hace con web empaquetada?
4. ¿El puesto de estación se bloquea con quiosco o con un programa instalado? ¿Quién reinstala?
5. ¿Qué se comparte de verdad entre las cuatro: pantallas, o solo el contrato de datos?
6. ¿Un fallo en la web pública obliga a publicar también la app?
7. ¿Qué permisos pide el teléfono y qué queda usable si se niegan?

Si la propuesta no puede responder, no ha elegido tecnología. Ha elegido un vocabulario.

## Qué no hace falta preguntar todavía

No hace falta el nombre de la librería de estado, ni si el Virtual DOM «es más rápido», ni el detalle de carpetas. Eso es el módulo siguiente, y se lee sobre las demos que sí existen. Aquí el cierre es de superficie.

Tampoco hace falta una demo de React Native para sostener el caso. Pedir ver la app arrancar antes de haber escrito el uso es invertir el orden: se vería un emulador y se seguiría sin saber si el viajero tiene que instalar.

## Puente con lo que sigue

Las piezas web —portada y panel— ya tienen código. El módulo de componentes lo abre por dentro: qué es una pieza, quién guarda el estado, cómo se separan las carpetas de la SPA y las de Next.js. Sin esa lectura, «componentes reutilizables» sigue siendo una frase de la propuesta. Con ella, se puede señalar el fichero.
